## 1. Application / account update envelope

- Name: `eppic_outcome_v1`
- Language: `en`
- Proposed category: `UTILITY` (Meta determines final eligibility)
- Body:

  > Eppic Pawn Shop has an update about your application or account: {{1}} Reply here if you need assistance.

- `{{1}}`: the actual update, generated by the existing owner-approved
  application/contract/repayment/extension/category/manual-message flow.
  Example: `The manager has approved your application at N$3,750.00.`

This is deliberately an envelope, not another decision engine. It never adds
an amount, changes an approval, or decides whether an item is accepted. It also
carries owner/staff operational updates when their own reply window is shut.
Tabs, line breaks and repeated spaces in parameters are normalised to spaces.
The original text remains available to the local simulator/transcript.

**Approval risk to review:** this is a broad variable-heavy template. Meta may
reject it or require distinct, more specific templates for customer outcomes,
contracts and internal alerts. These tests prove payload shape, not approval
eligibility. Do not deploy by assuming the generic envelope has been approved;
revise identifiers/mappings under a reviewed task if Meta requires a split.
Do not truncate a long application or signing link to force it through: a
rejection must be reported visibly instead.

## Runtime behaviour and callable service

All router sends, including `SAY`, outcomes, signing links, repayments,
extensions, forfeiture/category replies and owner alerts, use
`WindowAwareTransport`. It reads Claude's migration-14 `lastInboundAt(phone)`.
A valid Meta-sourced timestamp less than 24 hours old permits free-form text.
Exactly 24 hours, unknown, invalid, future or receipt-only times take the
template path. Sending a message never opens a window.

`Collections` is callable, **not scheduled**:

```ts
const waiting = [...router.collections.reminders(), ...router.collections.finalNotices()];
for (const notice of waiting) {
  const result = await router.collections.send(notice);
  // Inspect result.state; accepted means a provider ID, not delivered/read.
}
```

No existing request handler calls that loop. No timer is created. Task 008 must
decide hosting/scheduling and call it. The dashboard shows reminders and today's
final notices waiting, missed final-notice dates, plus failed or interrupted
attempts needing review. Viewing the dashboard sends nothing.

Eligibility is evaluated from today's UTC date, current due/grace dates,
active-loan status, unsold/unredeemed collateral and a positive ledger balance.
Reminder eligibility is the exact playbook lead-time date; there is no invented
late-reminder catch-up policy. Final notices are eligible only on the loan's
own grace-end date, which already includes the granted grace period. Nothing
is sent after that date. A candidate is re-read before sending; a loan paid
since listing is not chased. Both templates carry the freshly summed balance.
The final warning does not itself change a loan/item status or post a sale.

## Migration 15: why delivery needs memory

`collection_notices` has one row per loan and notice kind. It reserves the
attempt before network work and transitions from `sending` to `accepted` or
`failed`. A reservation is a unique database insert, so concurrent callers and
restarts cannot send the same notice twice. It stores no financial balance and
changes no ledger rows. Existing migrations and ledger triggers are unchanged.

There is no transaction held across a network request. This is **at-most-once
attempting**, not a false exactly-once delivery promise. If the process dies
after reservation or Meta accepts a message but its response is lost, delivery
is unknown. The reservation remains suppressed and visible for review; an
operator must inspect WhatsApp/provider logs rather than automatically resend.
The service does not supply a retry/reset command or delete history. A separate
reviewed recovery action is needed if a manual resend is appropriate.

Template POSTs and free-form collection notices each get one network attempt;
an ambiguous POST is not retried automatically. Other existing free-form sends
retain the transport's retry policy. Template rejections/missing names/language
or missing provider IDs throw errors. The router logs them and attempts an
owner alert through the same window-aware path. If the owner's alert also
fails, it is logged without recursive alerts. Collections failures also remain
visible on the dashboard. No free-form fallback is used outside the window.
